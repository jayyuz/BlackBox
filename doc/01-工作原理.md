# BlackBox 虚拟引擎工作原理

> 本文剖析 BlackBox 如何在**未安装**的情况下运行另一个 APK，以及它如何在不修改目标应用的前提下伪装出一个独立的 Android 运行时。
>
> 阅读对象：Android 系统开发、逆向、应用双开/沙箱方向的工程师。

---

## 一、问题的本质

Android 的正常应用模型是**一进程一应用一 UID**：

```
Zygote fork ──► ActivityThread.main() ──► 加载 /data/app/<pkg>/base.apk
                                          ──► Application.attach()
                                          ──► AMS 根据 PackageManager 的服务记录派发组件
```

要让应用 B 跑起来，需要同时满足四件事：

| 需求 | 由谁提供 |
|---|---|
| 代码能加载 | `LoadedApk` / `ClassLoader` / `DexFile` |
| 资源能解析 | `AssetManager` / `Resources` |
| 组件能被系统派发 | `PackageManagerService` 的组件表 |
| 数据能落盘且互不干扰 | 私有 data 目录 + 文件系统沙箱 |

一个未安装的 APK，这四项**全都没有**。

BlackBox 的做法是：**借用宿主的进程、UID 和已注册组件，把上面四项逐个"伪造"出来。**

核心思路可以概括成一句话：

> 让系统以为在启动宿主的一个占位组件，实际执行的却是目标应用的代码。

## 二、整体架构

### 2.1 模块划分

```
BlackBox/
├── app/                    UI 层（应用列表、双开管理、设置）
├── Bcore/                  ★ 核心引擎
│   ├── src/main/java/        虚拟系统服务 + Hook 层
│   ├── src/main/cpp/         原生 Hook（JNI / 文件系统 / Binder UID）
│   ├── src/main/aidl/        自研系统服务的 Binder 接口
│   ├── black-fake/           编译期占位：伪造 @hide 框架类
│   ├── black-hook/           JNI Hook 的 Java 声明层
│   ├── pine-core/            Pine（ART 方法级 Hook）
│   └── pine-xposed/          Xposed 兼容层
└── android-mirror/         ★ 反射镜像层（219 个类）
```

`android-mirror` 是这个项目最关键的设计之一，稍后详述。

### 2.2 三个进程角色

BlackBox 把宿主拆成三种角色，由 `BlackBoxCore` 在 `attachBaseContext` 阶段按进程名判定：

```java
// BlackBoxCore.java
String processName = getProcessName(getContext());
if (processName.equals(getHostPkg())) {
    mProcessType = ProcessType.Main;          // 宿主主进程：UI
} else if (processName.endsWith(getString(R.string.black_box_service_name))) {
    mProcessType = ProcessType.Server;        // ":black" 进程：虚拟 system_server
} else {
    mProcessType = ProcessType.BAppClient;    // ":pN" 进程：虚拟应用运行处
}
```

| 角色 | 进程名 | 职责 |
|---|---|---|
| **Main** | `host.pkg` | UI；不参与虚拟化逻辑 |
| **Server** | `host.pkg:black` | 虚拟的 `system_server`：包管理、活动管理、账户、定位、通知 |
| **BAppClient** | `host.pkg:p0` … `:p49` | 真正加载并运行目标 APK 代码 |

`Server` 进程承担了 Android 上 `system_server` 的角色，但它没有系统权限，所以它的"服务"其实是**普通的 Binder 对象**，通过一个 ContentProvider 暴露给客户端。

### 2.3 通信：为什么用 ContentProvider 而不是 Service

`BlackBoxCore.getService(name)` 拿到虚拟服务的 Binder：

```java
// BlackBoxCore.java:349
public IBinder getService(String name) {
    IBinder binder = mServices.get(name);
    if (binder != null && binder.isBinderAlive()) return binder;

    Bundle bundle = new Bundle();
    bundle.putString("_B_|_server_name_", name);
    Bundle vm = ProviderCall.callSafely(ProxyManifest.getBindProvider(), "VM", null, bundle);
    binder = BundleCompat.getBinder(vm, "_B_|_server_");
    mServices.put(name, binder);
    return binder;
}
```

用 Provider 而非 Service 有很实际的理由：

- `ContentProvider` 在**进程启动时由 `ActivityThread` 自动实例化**，无需 `bindService` 就能拿到 `IBinder`，省掉一次完整的服务绑定握手；
- 可以绕过 `bindService` 的许多权限/后台限制；
- `call()` 方法支持事务式参数传递。

对应的服务端是 `SystemCallProvider`，收到 `"VM"` 方法就返回对应服务的 Binder。

## 三、进程的诞生：从宿主到虚拟应用

这是整个引擎最精妙的一环。系统并不知道虚拟应用的存在，**它只看到宿主在启动自己的 `:pN` 进程**。

### 3.1 第一步：启动一个空壳进程

`BProcessManagerService.startProcessLocked()` 为目标应用分配一个空闲的 `bpid`（0–49）：

```java
// BProcessManagerService.java:110
private int getUsingBPidL() {
    for (int i = 0; i < ProxyManifest.FREE_COUNT; i++) {   // FREE_COUNT = 50
        if (usingPs.contains(i)) continue;
        return i;
    }
    return -1;
}
```

然后通过 ContentProvider 触发 `host.pkg:p{bpid}` 进程创建：

```java
// BProcessManagerService.java:155
private boolean initAppProcessL(ProcessRecord record) {
    AppConfig appConfig = record.getClientConfig();
    Bundle bundle = new Bundle();
    bundle.putParcelable(AppConfig.KEY, appConfig);
    Bundle init = ProviderCall.callSafely(record.getProviderAuthority(),
                                          "_Black_|_init_process_", null, bundle);
    IBinder appThread = BundleCompat.getBinder(init, "_Black_|_client_");
    if (appThread == null || !appThread.isBinderAlive()) return false;
    attachClientL(record, appThread);
    return true;
}
```

进程名形如 `host.pkg.p{0..49}`，与 manifest 中预先声明的 50 个 `ProxyContentProvider` 一一对应 —— 这是"多开 50 个实例"的物理基础。

### 3.2 第二步：在空壳进程里"扮演"目标应用

`ProxyContentProvider.call()` 收到初始化请求后，把 `AppConfig` 交给 `BActivityThread`：

```java
// ProxyContentProvider.java
if (method.equals("_Black_|_init_process_")) {
    AppConfig appConfig = extras.getParcelable(AppConfig.KEY);
    BActivityThread.currentActivityThread().initProcess(appConfig);
    Bundle bundle = new Bundle();
    BundleCompat.putBinder(bundle, "_Black_|_client_", BActivityThread.currentActivityThread());
    return bundle;
}
```

`BActivityThread` 是一个 `IBActivityThread.Stub`，相当于**虚拟进程的"本地 AMS 代理"**。它把 `AppConfig` 存下来（虚拟 uid、包名、进程名、用户 id…），此后所有对"我是谁"的询问都由它回答。

### 3.3 第三步：重建 Application 生命周期

真正的魔法在 `handleBindApplication()`：

```java
// BActivityThread.java:296
public synchronized void handleBindApplication(String packageName, String processName) {
    PackageInfo packageInfo = getBPackageManager().getPackageInfo(packageName, GET_PROVIDERS, userId);
    ApplicationInfo applicationInfo = packageInfo.applicationInfo;

    // 1. 用目标 APK 的路径创建 Context（CONTEXT_INCLUDE_CODE 会加载 guest 的 dex）
    Context packageContext = createPackageContext(applicationInfo);
    Object loadedApk = BRContextImpl.get(packageContext).mPackageInfo();

    // 2. 把 LoadedApk 里的 ApplicationInfo 换成 guest 的
    BRLoadedApk.get(loadedApk)._set_mSecurityViolation(false);
    BRLoadedApk.get(loadedApk)._set_mApplicationInfo(applicationInfo);

    // 3. 修正 targetSdk / StrictMode / WebView 数据目录
    BRVMRuntime.get(runtime).setTargetSdkVersion(applicationInfo.targetSdkVersion);
    WebView.setDataDirectorySuffix(userId + ":" + packageName + ":" + processName);

    // 4. 安装 IO 重定向
    NativeCore.init(Build.VERSION.SDK_INT);
    IOCore.get().enableRedirect(packageContext);

    // 5. 改写当前进程的 ActivityThread 状态，让它以为在启动 guest
    ActivityThreadAppBindDataContext bindData = BRActivityThreadAppBindData.get(boundApplication);
    bindData._set_appInfo(applicationInfo);
    bindData._set_info(loadedApk);
    bindData._set_processName(processName);

    // 6. 创建 guest 的 Application 并回调 onCreate
    Application application = BRLoadedApk.get(loadedApk).makeApplication(false, null);
    installProviders(application, processName, providers);
    AppInstrumentation.get().callApplicationOnCreate(application);
}
```

第 5 步是关键：**直接篡改 `ActivityThread` 的 `mBoundApplication`**。此后系统框架每次查询"当前进程绑定了哪个 App"，拿到的都是 guest 的信息。

第 6 步通过 `makeApplication` 触发 guest 的 `Application.attach()` / `onCreate()`，生命周期正式接管。

## 四、代码与资源：如何加载一个未安装的 APK

### 4.1 类加载

`createPackageContext(pkg, CONTEXT_INCLUDE_CODE | CONTEXT_IGNORE_SECURITY)` 让框架基于目标 APK 的路径构造 `LoadedApk` 与 `PathClassLoader`。因为 APK 已经被拷贝到宿主私有目录（`blackbox/data/app/<pkg>/base.apk`），路径可读，dex 就能正常加载。

### 4.2 资源解析

`PackageManagerCompat.getResources()` 手工构造 `AssetManager`：

```java
// PackageManagerCompat.java
public static Resources getResources(Context context, ApplicationInfo appInfo) {
    BPackageSettings ps = get().getBPackageSetting(appInfo.packageName);
    if (ps != null) {
        AssetManager assets = BRAssetManager.get()._new();
        BRAssetManager.get(assets).addAssetPath(ps.pkg.baseCodePath);
        Resources hostRes = context.getResources();
        return new Resources(assets, hostRes.getDisplayMetrics(), hostRes.getConfiguration());
    }
    return null;
}
```

用 `addAssetPath` 把 guest APK 挂进 `AssetManager`，再套用宿主的 `DisplayMetrics`/`Configuration`，就能正确解析 guest 的资源 ID。

## 五、组件虚拟化的核心：占位组件替换

这是理解 BlackBox 的关键。系统只会派发**已在自己组件表里注册**的组件。guest 的 Activity 不在表里，所以必须"偷梁换柱"。

### 5.1 两层替换

**第一层：在 AMS 调用处替换 Intent**

`ActivityManagerCommonProxy.StartActivity` 拦截所有 `startActivity`：

```java
ResolveInfo resolveInfo = getBPackageManager().resolveActivity(intent, GET_META_DATA, resolvedType, userId);
// 用自己的 ComponentResolver 解析 guest 的 Activity
intent.setComponent(new ComponentName(resolveInfo.activityInfo.packageName, resolveInfo.activityInfo.name));

getBActivityManager().startActivityAms(userId, ...);
    //      ↓ 内部
    //  Intent shadow = getStartStubActivityIntentInner(...)  // 换成 ProxyActivity$Pn
    //  Context.startActivity(shadow)                          // 交还给真实系统
```

`ActivityStack.startActivityProcess()` 构造出 `shadow` Intent：

```java
// ActivityStack.java:340
Intent shadow = new Intent();
shadow.setComponent(new ComponentName(getHostPkg(), ProxyManifest.getProxyActivity(vpid)));
ProxyActivityRecord.saveStub(shadow, intent, activityInfo, activityRecord, userId);
```

真实系统收到的是 `host.pkg/ProxyActivity$P12`，**完全合法**。而 guest 的原始 Intent、`ActivityInfo`、用户 id、token 都打包进了 extras：

```java
// ProxyActivityRecord.java:32
public static void saveStub(Intent shadow, Intent target, ActivityInfo info, IBinder record, int userId) {
    shadow.putExtra("_B_|_user_id_", userId);
    shadow.putExtra("_B_|_activity_info_", info);
    shadow.putExtra("_B_|_target_", target);
    BundleCompat.putBinder(shadow, "_B_|_activity_record_v_", record);
}
```

**第二层：在 Activity 真正创建前把 Intent 换回来**

`ProxyActivity.onCreate()` 立刻 `finish()` 自己，只留一个空壳。真正的替换发生在更早的 `Handler.Callback` 里：

```java
// HCallbackProxy.java:145
private boolean handleLaunchActivity(Object client) {
    Object r = getLaunchActivityItem(client);            // ClientTransaction 里的 LaunchActivityItem
    intent = BRLaunchActivityItem.get(r).mIntent();
    token  = BRClientTransaction.get(client).mActivityToken();

    ProxyActivityRecord stubRecord = ProxyActivityRecord.create(intent);
    // ... 绑定应用、登记 ActivityRecord ...

    // ★ 把 LaunchActivityItem 里的 Intent/Info 换成 guest 的
    LaunchActivityItemContext item = BRLaunchActivityItem.get(r);
    item._set_mIntent(stubRecord.mTarget);
    item._set_mInfo(stubRecord.mActivityInfo);
    return false;
}
```

`ActivityThread` 接下来会用这个已被改写的 `LaunchActivityItem` 构造 `ActivityClientRecord` 并执行 `handleLaunchActivity`。**从这一刻起，框架眼里就是 guest 的 Activity 在启动了**：

```
真实系统派发:  host.pkg/ProxyActivity$P12
                    ↓ (HCallbackProxy 改写 LaunchActivityItem)
框架实际启动:  com.tencent.mobileqq/.activity.SplashActivity
```

### 5.2 为什么需要 50 个占位类

`FREE_COUNT = 50`，于是有 `ProxyActivity$P0` … `P49` 共 50 个空壳子类，`ProxyService` 同样 50 个。

- **多实例**：同一应用多开、同一 Activity 多实例时，不同实例必须落在不同的占位组件上，否则系统会把它们视为同一个 task/实例；
- **多进程**：每个占位类在 manifest 里绑定到独立进程 `:p0` … `:p49`。

这是"支持 50 个虚拟应用同时运行"的物理来源。

### 5.3 为什么必须改写 `LaunchActivityItem` 而不是 `ActivityClientRecord`

在 Android 12 之前，可以这样拿到 record 再改：

```java
Object record = ActivityThread.getLaunchingActivity(token);
```

但 **Android 13 删除了 `getLaunchingActivity()`**，改名为 `getActivityClient()`。更关键的是时序：`mActivities.put(r.token, r)` 发生在 `handleLaunchActivity()` **内部**，而我们的回调在其**之前**执行 —— 此时按 token 查必然拿到 `null`。

所以正确做法是改写 `ClientTransaction` 中的 `LaunchActivityItem`：这是"请求"，`ActivityClientRecord` 是"结果"。改请求既无时序依赖，也不需要 API 版本分支。

## 六、Hook 体系

BlackBox 用了三套不同层次的 Hook，各有其不可替代的用途。

### 6.1 第一套：Binder 服务代理（Java 层）

**目标**：拦截应用对系统服务的调用，改用虚拟实现。

`ClassInvocationStub` 用 `java.lang.reflect.Proxy` 为系统服务接口生成代理，再通过反射把框架缓存的单例替换掉：

```java
// ClassInvocationStub.java:49
public void injectHook() {
    mBase = getWho();                                    // 原始 IActivityManager
    mProxyInvocation = Proxy.newProxyInstance(
            mBase.getClass().getClassLoader(),
            MethodParameterUtils.getAllInterface(mBase.getClass()),
            this);
    inject(mBase, mProxyInvocation);                     // 替换单例

    onBindMethod();                                      // 手工注册（少数）
    for (Class<?> c : getClass().getDeclaredClasses())
        initAnnotation(c);                               // 注解注册（多数）
}
```

```java
// IActivityManagerProxy.java:83
protected void inject(Object base, Object proxy) {
    Object singleton = BRActivityManagerOreo.get().IActivityManagerSingleton();
    BRSingleton.get(singleton)._set_mInstance(proxy);     // 偷换单例
}
```

拦截逻辑用注解声明，简洁且类型安全：

```java
@ProxyMethod("startActivity")
public static class StartActivity extends MethodHook {
    protected Object hook(Object who, Method method, Object[] args) { ... }
}
```

当前共有 **44 个**这样的代理类，覆盖 ActivityManager、PackageManager、TelephonyManager、LocationManager、AccountManager、NotificationManager 等。

### 6.2 第二套：JNI 方法 Hook（Native 层）

**目标**：拦截**不在 Java 层暴露**的调用 —— 尤其是 `java.io.UnixFileSystem` 的 native 方法和 `Binder.getCallingUid()`。

`JniHook` 的做法是直接改写 `ArtMethod` 结构体里的 native 函数指针：

```cpp
// JniHook.cpp
auto artMethod = reinterpret_cast<uintptr_t *>(GetArtMethod(env, clazz, method));
*orig_fun = reinterpret_cast<void *>(artMethod[HookEnv.art_method_native_offset]);
env->RegisterNatives(clazz, gMethods, 1);       // 用新函数重新注册
```

难点在于 `art_method_native_offset` 和 `art_method_flags_offset` 是**运行时探测**出来的，因为 ART 的 `ArtMethod` 布局随版本变化、且被混淆：

```cpp
// 利用两个相邻声明的 native 方法，其指针差 = sizeof(ArtMethod)
HookEnv.art_method_size = (size_t)((char*)nativeOffset2 - (char*)nativeOffset);
const size_t slots = HookEnv.art_method_size / sizeof(uintptr_t);

// 扫描找到存着 native_offset 函数指针的那个槽位
for (size_t i = 0; i < slots; ++i) {
    if (reinterpret_cast<void*>(artMethod[i]) == native_offset) {
        HookEnv.art_method_native_offset = (int) i;
        break;
    }
}
```

这套机制不依赖符号表、不依赖私有偏移常量，因此在多个 Android 版本上都能工作。

### 6.3 第三套：Pine（ART 方法级 Hook）

用于 Xposed 兼容层，也是 `pine-xposed` 模块的基础 —— 允许加载第三方 Xposed 模块并 `hookMethod`。

注意：本项目**没有**用 Pine 做权限拦截。Pine 的 `ensureInitialized()` 在虚拟进程内会死锁（详见迁移文档），因此权限走的是 Binder 层。

### 6.4 镜像层：`android-mirror`

这是最容易被忽视但最关键的基础设施。

**问题**：`android.app.ActivityThread`、`android.content.pm.IPackageManager`、`IActivityManager$ContentProviderHolder` 等都是 `@hide`。直接 `import` 编译不过，`Class.forName` 在某些类加载器下也找不到。

**方案**：定义与框架同签名的接口，用注解描述字段/方法，由注解处理器生成反射代码。

```java
// android-mirror/.../black/android/app/ActivityThread.java
@BClassName("android.app.ActivityThread")
public interface ActivityThread {
    @BField    Object mBoundApplication();
    @BField    Map<IBinder, Object> mActivities();
    @BField    Application mInitialApplication();
    @BMethod   Object getSystemContext();
    @BStaticField IInterface sPackageManager();

    @BClassName("android.app.ActivityThread$H")
    interface H {
        @BStaticField int EXECUTE_TRANSACTION();
        @BStaticField int CREATE_SERVICE();
    }
}
```

注解处理器生成 `BRActivityThread`：

```java
public static ActivityThreadContext get(final Object caller) {
    return BlackReflection.create(ActivityThreadContext.class, caller, false);
}
```

调用侧写起来像普通 getter：

```java
BRActivityThread.get(mainThread).mBoundApplication()      // 读字段
BRContextImpl.get(ctx)._set_mPackageManager(proxy)        // 写字段
BRLaunchActivityItem.get(item)._set_mIntent(intent)
```

**219 个镜像类**覆盖了 AMS、PMS、NotificationManager、ServiceManager、AssetManager 等几乎所有需要的私有 API。这是整个项目的"类型安全反射层"。

配套的 `black-fake`（14 个类）解决另一个问题：某些 `@hide` 类在**编译期**需要存在才能通过编译（如 `android.content.pm.PackageParser` 的常量），运行时再靠反射命中真实类。

## 七、数据隔离：文件系统重定向

应用 B 调用 `getFilesDir()` 应该拿到**自己的**目录，而不是宿主的。但 guest 与宿主同 UID，路径天然相同。

BlackBox 在 **native 层拦截所有 `java.io` 操作的入口**，把路径改写到虚拟根目录。

### 7.1 重定向规则

`IOCore.enableRedirect()` 建立规则表：

```java
rule.put("/data/data/" + pkg, packageInfo.dataDir);                    // → blackbox/data/user/0/<pkg>
rule.put("/data/user/0/" + pkg, packageInfo.dataDir);
rule.put("/sdcard", external.getAbsolutePath());                       // → blackbox/storage/emulated/0
rule.put("/storage/emulated/0", external.getAbsolutePath());
if (isHideRoot()) hideRoot(rule);   // /system/bin/su → /system/bin/su-fake ...
```

规则同时下发给 Java 层（`TrieTree` 做前缀匹配）和 native 层（`NativeCore.addIORule`）。

用 **Trie 树**而不是简单 `startsWith` 循环，是因为规则多、路径长、调用极其频繁（每次 `File.exists()` 都要查）。

### 7.2 native 拦截点

`UnixFileSystemHook` 拦截了 `java.io.UnixFileSystem` 上所有 native 方法：

```cpp
void UnixFileSystemHook::init(JNIEnv *env) {
    JniHook::HookJniFun(env, "java/io/UnixFileSystem", "canonicalize0",     "(Ljava/lang/String;)Ljava/lang/String;", ...);
    JniHook::HookJniFun(env, "java/io/UnixFileSystem", "getLastModifiedTime0", ...);
    JniHook::HookJniFun(env, "java/io/UnixFileSystem", "list0", ...);
    JniHook::HookJniFun(env, "java/io/UnixFileSystem", "createDirectory0", ...);
    // ... setPermission0 / createFileExclusively0 / setReadOnly0 / getSpace0 ...
}
```

每个 hook 的实现模式都一样：

```cpp
HOOK_JNI(jobjectArray, list0, JNIEnv *env, jobject obj, jobject file) {
    jobject redirect = IO::redirectPath(env, file);     // 改写路径
    return orig_list0(env, obj, redirect);              // 调原函数
}
```

**为什么选这一层**：`java.io.File` 的所有最终操作都汇聚到 `UnixFileSystem` 的少数几个 native 方法。在这里拦截一次，就覆盖了 `File`、`FileInputStream`、`FileOutputStream`、`SharedPreferences`、SQLite 等所有上层 API —— 而不需要 hook 几十个 Java 方法，也不会被应用绕过。

### 7.3 为什么还要 `canonicalize0`

其余 hook 改写的是"操作路径"，但 `canonicalize0` 改写的是"路径规范化结果"。如果不拦截它，应用调用 `File.getCanonicalPath()` 会拿到真实路径，从而：

- 泄露宿主真实目录结构；
- 后续用规范化路径做的检查（如白名单校验）会失效。

## 八、身份伪装：UID 与虚拟用户

### 8.1 虚拟 UID

每个装入的应用被分配一个虚拟 appId，从 `FIRST_APPLICATION_UID` 开始递增：

```java
// Settings.java:113
private int acquireAndRegisterNewAppIdLPw(BPackageSettings obj) {
    Integer integer = mAppIds.get(obj.pkg.packageName);
    if (integer != null) return integer;
    if (mCurrUid >= Process.LAST_APPLICATION_UID) return -1;
    mCurrUid++;
    mAppIds.put(obj.pkg.packageName, mCurrUid);
    return Process.FIRST_APPLICATION_UID + mCurrUid;      // 10000 + n
}
```

真实进程的 uid 始终是宿主的，但应用通过 `Process.myUid()`、`getCallingUid()` 看到的是虚拟 uid。

### 8.2 拦截 `Binder.getCallingUid`

```cpp
// BinderHook.cpp
HOOK_JNI(jint, getCallingUid, JNIEnv *env, jobject obj) {
    int orig = orig_getCallingUid(env, obj);
    return BoxCore::getCallingUid(env, orig);
}
```

```java
// NativeCore.java:53
public static int getCallingUid(int origCallingUid) {
    if (origCallingUid < Process.FIRST_APPLICATION_UID) return origCallingUid;   // 系统 uid 不动
    if (origCallingUid > Process.LAST_APPLICATION_UID)  return origCallingUid;
    if (origCallingUid == getHostUid()) {
        return BActivityThread.getCallingBUid();          // 宿主 uid → 虚拟调用方 uid
    }
    return origCallingUid;
}
```

这样应用用 `Binder.getCallingUid()` 做身份校验时，看到的是"另一个虚拟应用"的 uid，而不是"宿主"的。

### 8.3 虚拟用户

`BUserManagerService` 支持多用户空间，每个用户有独立的 `data/user/<userId>/` 目录。虚拟 uid 由 `BUserHandle.getUid(userId, appId)` 组合而成，与系统的 uid 编码规则一致（`userId * 100000 + appId`）。

## 九、隐藏对抗

### 9.1 隐藏 Root

`IOCore.hideRoot()` 把 su 相关路径重定向到不存在的 `-fake` 路径：

```java
rule.put("/system/bin/su",   "/system/bin/su-fake");
rule.put("/system/xbin/su",  "/system/xbin/su-fake");
rule.put("/sbin/su",         "/sbin/su-fake");
rule.put("/su/bin/su",       "/su/bin/su-fake");
// ...
```

应用执行 `new File("/system/bin/su").exists()` 时，native hook 把路径改成 `su-fake`，返回 `false`。

### 9.2 隐藏 Xposed

Xposed 模块以 dex 形式加载进虚拟进程，类名会暴露痕迹。`VMClassLoaderHook` 在类加载阶段过滤：

```cpp
HOOK_JNI(jobject, findLoadedClass, JNIEnv *env, jobject obj, jobject loader, jstring name) {
    if (hideXposedClass) {
        if (strstr(nameC, "de/robv/android/xposed/") ||
            strstr(nameC, "me/weishu/epic")        ||
            strstr(nameC, "me.weishu.exposed")) {
            return nullptr;                   // 假装从未加载过
        }
    }
    return orig_findLoadedClass(env, obj, loader, name);
}
```

这是 README 中"XposedChecker / XposedDetector 检测不到"的技术来源。

### 9.3 隐藏进程身份

```java
// VirtualRuntime.java
BRProcess.get().setArgV0(processName);              // /proc/self/cmdline
BRDdmHandleAppName.get().setAppName(processName, 0);
```

同时 `IOCore.proc()` 把 `/proc/self/cmdline` 也重定向到虚拟进程目录，避免应用读 `/proc` 发现真实进程名是 `host.pkg:pN`。

## 十、虚拟系统服务

`Server` 进程里运行着一套精简版的 `system_server`：

| 虚拟服务 | 对应系统服务 | 作用 |
|---|---|---|
| `BActivityManagerService` | ActivityManager | Activity/Service 栈管理，组件替换 |
| `BPackageManagerService` | PackageManager | 组件表、权限表、应用安装 |
| `BUserManagerService` | UserManager | 虚拟用户 |
| `BAccountManagerService` | AccountManager | 账户隔离（1800+ 行，最复杂） |
| `BLocationManagerService` | LocationManager | 虚拟定位 |
| `BNotificationManagerService` | NotificationManager | 通知转发 |
| `BStorageManagerService` | StorageManager | 存储卷信息 |
| `BXposedManagerService` | — | Xposed 模块管理 |

### 10.1 Activity 栈

`ActivityStack` 自建了 `TaskRecord` / `ActivityRecord`，模拟系统的任务栈语义：

```java
// ActivityStack.java:112
public int startActivityLocked(int userId, Intent intent, String resolvedType, ...) {
    ResolveInfo resolveInfo = getBPackageManager().resolveActivity(intent, GET_ACTIVITIES, ...);
    ActivityInfo activityInfo = resolveInfo.activityInfo;

    switch (activityInfo.launchMode) {
        case LAUNCH_SINGLE_TOP:
        case LAUNCH_MULTIPLE:
        case LAUNCH_SINGLE_TASK:   taskRecord = findTaskRecordByTaskAffinityLocked(...); break;
        case LAUNCH_SINGLE_INSTANCE: taskRecord = findTaskRecordByTaskAffinityLocked(...); break;
    }
    // ... clearTop / singleTop / clearTask 语义 ...
    // → startActivityInNewTaskLocked 或 startActivityInSourceTask
}
```

`launchMode`、`FLAG_ACTIVITY_CLEAR_TOP`、taskAffinity 等语义都被手工实现了 —— 因为真实系统看到的是 50 个 `ProxyActivity$Pn`，它无法理解 guest 的 Activity 关系。

### 10.2 包管理

`BPackageManagerService` 在安装时用 `PackageParser` 解析 APK，把组件表、权限、签名抽出来存成自己的 `BPackage`：

```java
// Settings.java:241
private PackageParser.Package parserApk(String file) {
    PackageParser parser = PackageParserCompat.createParser(new File(file));
    PackageParser.Package aPackage = PackageParserCompat.parsePackage(parser, new File(file), 0);
    PackageParserCompat.collectCertificates(parser, aPackage, 0);
    return aPackage;
}
```

`PackageParser` 本身也是 `@hide` 且签名随版本变化，所以 `PackageParserCompat` 为每个 Android 版本写了不同分支（Lollipop / M / N / Pie / …）。

## 十一、完整启动时序

把上面所有环节串起来，启动一个虚拟应用的完整流程如下：

```

       │
②  └─ BPackageManager.getLaunchIntentForPackage()  →  Intent
       │
③  └─ ActivityManagerCommonProxy.StartActivity.hook()
        ├─ 用虚拟 PMS 解析出 SplashActivity
        └─ 转 BActivityManager
             │
④       └─ [Server 进程] ActivityStack.startActivityLocked()
            ├─ 建 ActivityRecord / TaskRecord
            ├─ BProcessManagerService.startProcessLocked()
            │     ├─ 分配 bpid = 12
            │     └─ ProviderCall → 触发 host.pkg:p12 进程创建
            ├─ shadow Intent → host.pkg/ProxyActivity$P12
            └─ Context.startActivity(shadow)          ← 交给真实系统
                     │

       │

        └─ BActivityThread.initProcess(AppConfig)     ← 记住"我是 QQ"
       │

                     │

```

## 十二、设计取舍与代价

这个架构用"最小侵入"换取了"最大兼容性"，代价也很明确：

| 设计 | 收益 | 代价 |
|---|---|---|
| 借用宿主 UID | 无需 root、无需系统权限 | 无法真正隔离数据；权限必须复用宿主 |
| 占位组件替换 | 无需修改目标 APK | 只能支持 50 个实例；launchMode 需自行实现 |
| Provider 做 IPC | 免 bindService、启动快 | 依赖 Provider 自动实例化时机，脆弱 |
| native hook `UnixFileSystem` | 一处拦截覆盖所有 IO | 与 ART/libcore 实现强耦合，每个大版本都可能变 |
| 反射镜像层 | 类型安全、可读性好 | 219 个类需随框架演进而维护 |
| 运行时探测 `ArtMethod` 偏移 | 跨版本、抗混淆 | 依赖"两个相邻方法"的假设，脆弱 |

最后一点尤其值得强调：第 7 节提到的 `canonicalize0`，在 Android 15 中签名从 `(String)` 变成了 `(String, boolean)`——**一处 libcore 改动就会让整个 IO 重定向失效**。这就是为什么这个项目每跟进一个 Android 大版本，都需要一轮系统的适配工作。
